TASK 1 — `--sweep` must refuse a field name that is not a config field (finding #3)
====================================================================================
The lever that silently measures nothing, in a tool whose entire product is the measurement.

  --sweep=stopLoss:-12          S:stopLoss=-12     20 trade  PF 3.25  $500.64  DD 10.6%  vs A  $0.00
  --sweep=stopLossPct:-12       S:stopLossPct=-12  16 trade  PF 6.95  $531.31  DD  9.6%  vs A +$30.67

Baseline A on the same cache and window: 20 trade, PF 3.25, $500.64, DD 10.6%. The typo row is
identical to the baseline in every column and prints `vs A $0.00` — which reads as "this lever
does nothing", when in fact the flag never applied.

`sweepScenarios` (`scripts/scenarioLab.ts:357-375`):

    const key = field.trim() as keyof BacktestConfig;
    ...
    out.push({ ... { config: { ...base, [key]: value } as BacktestConfig } });

The cast asserts a key that was never checked, so an unknown name becomes an inert extra property
on the config object. Nothing downstream can tell.

FIX. Validate the field name against the config BEFORE any scenario runs and throw with a message
that names: the offending field, the closest valid field when one is close (`stopLoss` ->
`stopLossPct`), and the full list of sweepable keys. Derive the allowed set from the base config
object itself, not from a second hard-coded list, so the two cannot drift apart.

TASK 3 — a raw token amount must not pass through `Number` on the money path (finding #1)
=========================================================================================
Three token -> SOL sites, all confirmed:

  `src/services/liveExecution.ts:1844`   `amountLamports: Number(current)`   auto-unwind after a failed open
  `src/services/liveExecution.ts:2341`   `amountLamports: Number(amount)`    the sweep's quote
  `src/services/liveExecution.ts:2350`   `amountLamports: Number(amount)`    the sweep's sale

while the SAME deps object passes `amount.toString()` for the pool route (`:2361`, `:2370`). Your
"one quantity, two conversions" tell is confirmed and it is the reason to fix this.

FIX — minimal and fail-closed:
  * The exact raw amount must reach the Jupiter boundary as bigint/string, the way the pool route
    already does. The quote and the sale must be built from the SAME exact value; today each
    rounds independently, so they can disagree with each other as well as with the balance.
  * If a `number` caller cannot be represented exactly, THROW. Never round silently: an
    over-request is refused by the token program, the sweep then pages the operator, and the
    capital stays in the token — which is the one failure this ladder exists to prevent.
  * Boundary test: balances at 2^53-1, 2^53, 2^53+1 and a non-representable value above it.
    Assert the requested amount, as a string, is <= the balance as a bigint, and that nothing
    rounds up. This test must FAIL against today's code for the non-representable case.
  * In your status, rank this by the measured distance, not by the hypothetical: the largest
    residual ever recorded is 4.5e9 raw units (2 million times below the threshold), the threshold
    needs a token priced below $2.1e-14 at a $189 cap, and the single production exercise of the
    auto-unwind (attempt id 5) passed an exact amount. Fix it — it is two lines and it is on the
    exit path — but I do not want a HIGH whose trigger needs a $1e-14 token.
