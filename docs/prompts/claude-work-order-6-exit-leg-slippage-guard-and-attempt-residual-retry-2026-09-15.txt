TASK 1 — THE BUG: an exit-leg quote is authorised against the ENTRY bound
=========================================================================
`src/services/onchainExecutor.ts:1278` in `buildJupiterSwap`:

    if (quote.slippageBps > auth.maxSlippageBps) {
      throw new ExecutionLimitError(
        `Jupiter returned a quote at ${quote.slippageBps} bps slippage, above the ` +
          `authorized ${auth.maxSlippageBps} bps`,
      );
    }

`auth.maxSlippageBps` is the ENTRY bound (50 bps, HARD_MAX_SLIPPAGE_BPS). But the quote was
fetched by `executeJupiterSwap` (`onchainExecutor.ts:1373`) with

    params.leg === "exit" ? resolveExitSlippageBps(params.slippageBps, config) : …

which resolves against `EXIT_MAX_SLIPPAGE_BPS` (default 300, HARD_MAX_EXIT_SLIPPAGE_BPS).
So EVERY exit-leg swap whose bound is wider than the entry bound builds a quote the guard
then refuses. Consequences, all real:

  * The auto-unwind in `liveExecution.ts:1841` (`leg: "exit"`, "auto-unwind after a failed
    open") can NEVER sell when the exit cap is 300 and the entry cap is 50 — which is the
    configured default. That is step 5 above.
  * The sweep ladder in `sweepResidualPairedToken` (`liveExecution.ts:2229`, rungs
    50 -> 150 -> 300) is effectively a ONE-RUNG ladder: rung 1 passes the guard, rungs 2 and
    3 throw exactly here. The "wider rather than repeated at the same width" behaviour the
    interface documents (ResidualSweepDeps.swapToSol) does not exist in production.
  * The comment at `onchainExecutor.ts:1360-1367` documents the intent ("Set it for the
    residual sale after a close and for the auto-unwind after a failed open") and the guard
    contradicts it. Same for `resolveExitSlippageBps`'s own doc block: "Refusing an entry
    costs nothing; refusing an exit strands the position's value."

FIX: the guard must compare against the SAME bound the quote was built with, i.e. carry the
resolved bound (or the leg) into `buildJupiterSwap` and compare
`quote.slippageBps > <that bound>`. Do NOT simply delete the check and do NOT widen
`auth.maxSlippageBps`: the entry bound must stay hard for entries — an over-wide entry is
the failure mode it exists to prevent. Keep it fail-closed: an exit quote above the EXIT cap
still throws.

TASK 3 — the residual of a failed open must be retried by the self-heal, not only by hand
========================================================================================
Tonight's token was recoverable only because a human ran a script. `retryResidualSweep.ts`
(and therefore the `*/2` Hermes self-heal cron) only looks at `simulated_positions` rows
(`residual_sweep IN ('failed','unmeasured')`), so an attempt-level orphan — a failed open
with no position row at all — is out of scope. Fold that case in:

  * Extend `scripts/retryResidualSweep.ts` to also select `live_execution_attempts` rows with
    `outcome='failed'`, `unwind='orphan'`, attempted within `--max-age-hours` (48) — the
    shape where the engine could not put the capital back.
  * Keep the existing chain guards: the position account must be ABSENT (if it exists, that
    is `recoverFundedOrphan.ts`'s job, not this one) and the pool must have no active
    position / no attempt in the last 15 minutes.
  * Sell through the SAME `sweepResidualPairedToken` + `defaultResidualSweepDeps` path.
  * When the sale lands, write the attempt row the way `settleRecoveredAttempt.cjs` does and
    only when the chain agrees: `cost_lamports` = measured real cost
    (`wallet_lamports_before - balance now`), `unwind='clean'`, `wallet_lamports_after` =
    measured balance. Use the script's own proof check — do not invent a new one.
  * Absorb `scripts/sweepAttemptResidual.ts` (my hand-run version, commit c93e413) into that
    flow or delete it in favour of it; keep exactly one sell path.
  * ATC/rent: a Token-2022 ATA with a non-zero withheld fee balance cannot be closed
    (tonight: `Error: An account can only be closed if its withheld fee balance is zero`).
    `closeEmptyTokenAccount` should report that as a distinct outcome, not throw, so the
    retry loop does not treat "rent not reclaimed" as "sale failed".

TASK 4 — the sizing guard did not cover the chunk that failed
============================================================
Tonight's refusal came from the `2/2` chunk (`Instruction 6: RebalanceLiquidity`) as
`custom program error: 0x1`, which this repo already decodes as InsufficientFunds
(`onchainExecutor.ts:963` — "the deposit asked to move more of the paired token"), and
`liveSizingGuard.ts` exists precisely to catch that shape ("Simulates every funding chunk and
reports the FIRST refusal caused by insufficient funds"). It ran and it did not prevent this.
So: check why the guard did not shrink the failing chunk — the likely hole is that the guard
sizes against the balance read BEFORE the balancing swap confirmed, while the `2/2` rebalance
runs AFTER it with a stale token amount (the swap delivered 40 376.32 LEVERCAT; the position
only ever got 14 577.09 of it). If the guard only simulates pre-swap, size the later chunk
against a RE-READ balance, or shrink-and-rebuild it once, and page the operator if the second
attempt is refused too. This is the half-landing that costs money in all three incidents, so
it is the highest-value half of this work order.
